# 리뷰 체크리스트

[코드 리뷰 절차](agents.md#코드-리뷰) · [꼭 지킬 것](../../AGENTS.md#꼭-지킬-것) · [출력 규약](output-contract.md) · [웹 화면과의 대응](provider-conventions.md#웹-화면과의-대응)

리뷰에서 나온 버그 패턴과 되풀이될 오탐을 관점별로 모은다. 2026-11-23 에 만들었다. 사례가 없는 항목은 리뷰에서 나오는 대로 사례를 더한다.
리뷰어는 여섯 관점 절의 항목을 하나씩 바뀐 코드에 대 보고(해당 없는 항목은 건너뛴다), 그다음 목록에 없는 문제도 찾는다.
코드·문서를 고친 쪽(작업자·주 에이전트)도 끝내기 전에 자기 변경에 **언제** 신호가 있는 항목을 대 본다 ([검증 분담](agents.md#검증-분담)).
규칙 자체는 위 링크 문서에 있고 여기에는 옮겨 적지 않는다.

- 항목의 **언제** 는 그 항목을 볼 diff 의 신호다. 신호가 있으면 그 자리를 **확인** 대로 따라가고, 신호가 없어도 바뀐 코드가 그
  항목의 흐름에 닿으면 본다. 항목은 `<관점 키>-<번호>`(예: `correctness-4`)로 부른다.
- 진짜 문제의 가장 큰 덩어리는 **출력 값은 맞는데 안내(`notes`·`hint`)가 틀린 것**이다. 관점과 상관없이 첫 질문은 "이 안내를
  그대로 따라 하면 성공하는가" 다.
- 사례 경로는 `src/baenggipyo/` 기준이고 줄 번호는 적은 날의 것이라, 어긋나면 그 자리 주석의 날짜나 이름으로 찾는다.
- 새 패턴을 더하는 법은 [코드 리뷰](agents.md#코드-리뷰) 6단계다.

## `correctness` 정확성·버그

1. **폴링·스트림·쪽 넘기기의 멈춤 조건.** 서버가 "더 있음" 이라면서 다음을 주지 않는 경우에 멈추고 알리는가. 스카이스캐너 폴링이
   끝났다는 표시 없이 같은 응답을 되풀이하거나 빈 응답만 주는 경우, 네이버 SSE 가 마지막 이벤트 없이 끊기는 경우다. 되풀이된 응답은
   세기 전에 멈추고, 정상 마지막 응답을 되풀이로 보지 않는다. 확인: 루프의 `break`·상한 조건을 그 입력들로 따라가 `notes`·센 수를 본다.
   언제: 폴링·스트림 읽기·`limit` 까지 받는 루프나 그 멈춤 조건을 바꾼 diff.
2. **"더 있음" 을 무엇으로 정하나.** "더 있을 수 있다" 안내는 받은(확인한) 수로 정한다. 거른 뒤 돌려준 수나 거르기 전에 센 수와 견주지
   않는다. 서버가 준 총수가 받은 수보다 커도 서버가 더 줄 것이 없으면 더 있음이 아니다. 확인: "다 받고 1건 뺌" 과 "`limit` 에 닿고
   1건 뺌" 으로 따라간다. 언제: "더 있음" 안내·`returned`·`total` 을 정하는 줄이나 결과를 빼는(거르는) 줄을 바꾼 diff.
3. **덜 받은 것을 "전부·없음" 으로 단정.** 끝나지 않은 폴링 결과나 상한에 닿은 목록의 수를 전체 수로 쓰거나, 남았는데 "없습니다"·
   "이 N건이 전부" 라고 하지 않는가 (검색이 끝나지 않았다는 안내나 `null` 로 알린다). 확인: 수·'없'·'전부' 가 든 안내마다 그 수가 끝까지
   받은 수인지 본다. 언제: 수를 담은 안내('건'·'없'·'전부')나 총수를 쓰는 `+` 줄.
4. **후보를 다 모은 뒤 판정하나.** "하나뿐"·"없음"·"이름이 같은 것이 여럿" 을 판정하는 후보 목록(공항·도시)이 그 시점에 완전한가.
   - 거른 뒤 개수를 세지 않는가 (같은 공항을 가리키는 도시 후보와 공항 후보를 따로 세어 `AIRPORT_AMBIGUOUS` 로 멈추거나, 여럿인데 하나를
     말없이 고르지 않는다).
   - 여럿일 때 일찍 멈춰 빠뜨리지 않는가, 에러에 합친 이름이 아니라 실패한 이름을 대는가.
   - 전체 수는 거르기 전 목록으로 셌어도 그 안의 하위 판정(정확히 같은 이름 하나 고르기 등)을 거른 목록에서 세지 않는가.

   확인: 후보 목록에 걸린 `len(...) == 1`·`break`·`next(...)`·`[0]` 자리마다 그 목록이 어디서 왔는지 거슬러 본다.
   언제: 후보 목록에 `len(...) == 1`·`next(`·`[0]`·`break` 가 걸린 `+` 줄, 또는 이름·코드로 후보를 고르거나 거르는 줄.
5. **누락값과 0.** 실패·모름은 `null`, 해당 없음은 키 삭제, 정말 빈 것만 `[]` 인가. `or`·`or 0`·`if not x` 로 0 과 모름을 섞지 않는가
   (수하물 정보가 없는 운임을 "포함 안 함" 으로 내지 않는다). 시각·항공사 이름 자리에서 `'-'`·빈 글자를 그대로 내지 않는가. 확인: 새
   `or ...`·truthiness·기본값 `[]`·`except` 가 돌려주는 값을 본다. 언제: `+` 줄에 `or `·`if not `·`else None`·기본값 `[]`·값을 돌려주는
   `except` 가 있을 때, 출력 필드를 더하거나 바꾼 diff.
6. **서버 값 한 칸이 결과 전체를 깨뜨림.** 서버 글자·목록·헤더를 `int()`·`[0]`·`del`·`.encode` 로 바로 다루지 않는가 (그 칸만 `null`·
   건너뛰기여야 한다). 확인: diff 의 그 호출과 Optional 아닌 list 필드에 빈 글자·'-'·null·소수를 넣어 본다. 언제: 서버 값에 `int(`·
   `float(`·`[0]`·`del `·`.split(`·`.encode` 를 바로 쓰는 `+` 줄, `api/response/` 의 필드 자료형을 바꾸거나 응답 모델을 새로 더한 diff.
7. **지운 줄이 받던 입력.** `git diff` 의 `-` 줄이 받던 꼴(더 짧은 날짜, 다른 구분자, 빈 값)을 `+` 줄도 받는가. 고친 코드가 예전보다
   정보를 버리면 퇴보다. 확인: 지운 분기와 새 분기에 같은 입력을 넣어 비교한다. 언제: 파싱·분기·검사의 `-` 줄을 다른 코드로 바꾼 diff
   (지우기만 한 줄도).
8. **실패·취소 경로 (주로 `core/`).** 예외·Ctrl+C·다른 프로세스와 겹칠 때 잠금·상태 파일을 정리하는가, 다른 프로세스가 새로 쓴 파일을
   덮지 않는가, 잠깐의 실패에 오래 남는 상태를 만들지 않는가. 우리 프로세스가 끝난 뒤에도 자식 프로세스(Chromium)가 닫히며 파일을 다시 쓸 수 있어 프로세스 안
   정리(`finally`·`atexit`)만으로는 임시 폴더가 남을 수 있다. 확인: 실제로 Ctrl+C 로 끊고 몇 초 뒤 남은 폴더를 센다. 예: `core/browser.py:662`
   `_sweep_temp_profiles` (그때 `atexit` 로 지운 임시 기록 폴더를 Chromium 이 다시 만들어 다음 명령이 치우게 했다, 2026-11-24 리뷰).
   언제: `core/` 의 `try`·`except`·`finally`·잠금·파일 쓰기를 바꾼 diff.
9. **공백뿐이거나 앞뒤 공백이 붙은 사용자 입력.** 앞뒤 공백을 떼지 않으면 이름 비교(`==`·`endswith`)가 어긋나 맞는 후보를 못 찾는다.
   공백만 있는 입력이 길이 검사를 지나면 `.split()[-1]`·`[0]` 이 IndexError(`INTERNAL_ERROR`)가 된다. 서버가 빈 응답을 줘서 지금
   안 닿는 것은 막는 이유가 아니다. 확인: `' '` 를 넣어 그 줄까지 따라간다. 언제: 사용자 검색어에 `.split()`·인덱스를 쓰는 줄을 조건
   밖으로 옮기거나 새로 더한 diff.
10. **묶음 한 줄의 대표 값과 고른 `id`.** 서버가 여러 판매처 운임이나 여러 항공권을 한 줄로 묶어 줄 때 그 줄의 가격·판매처 같은 필드는
    묶음 안 어느 것의 값인지 보고, 대표를 고르는 순서가 `id` 와 다르면 `id` 와 그 필드가 다른 것을 가리킨다. 소스가 값을 주지 않은 칸을 `null`
    로 비워 두고 다른 곳에서 채우지 않으면 늘 `null` 인 필드가 된다. 확인: 묶음이 섞인 원본 응답에서 목록 순서와 대표 필드를 대 보고, 줄의
    필드를 `flight` 상세와 견준다. 예: `providers/naver/service/domestic.py:688` `_offer` (그때 국내선 왕복 `flight` 의 따로 예약 조합 줄
    `price_per_adult_krw` 가 늘 `null` 이었다. 지금은 `per_adult` 로 채운다, 2026-11-01).
    언제: 묶음 줄에 필드를 더하거나 묶인 것 중 대표를 고르는 순서를 정·바꾸는 diff.
11. **해당 없음으로 키를 뺀 필드에 조건을 걸 때.** 키를 뺀 항목도 내부 값은 `None` 이라 거르기가 '모름' 처럼 조용히 뺀다. 그 조건으로 뺀
    해당 없음 항목을 `notes` 로 알리거나 문서에 적었는가. 확인: `not_applicable_fields` 와 같은 필드의 거르기 함수를 나란히 보고, 그 항목이
    있는 조건으로 불러 `notes` 를 본다. 언제: `not_applicable_fields` 에 값에 따라 빠지는 키를 더하는 diff, 또는 그런 필드에 거르기 조건을
    더하는 diff.
12. **모르는 값을 같은 diff 안에서 같은 기준으로 다루는가.** 값이 `None`·빈 글자일 때 한 곳은 '요청하지 않음', 다른 곳은 '요청함' 이거나 한
    필드는 키를 빼고 다른 필드는 `null` 로 두지 않는가. 확인: 같은 입력(`None`, `''`)을 요청 조건·키 제거 조건·출력 값 세 곳에 넣어 같은 결론인지
    본다. 언제: '있는지 모르는' 값으로 요청이나 키 제거를 정하는 `+` 줄, 같은 값을 읽는 조건이 둘 이상 생긴 diff.
13. **서버가 정렬해 준 목록을 걸러 쓸 때 '더 있음'.** 서버가 거르는 값으로 정렬해 주는 목록에서 그 값이 있는 것만 남기면, 받은 수가 상한에
    닿았어도 꼬리가 걸러지는 값이면 걸러 남을 것이 더 없다. 받은 수만으로 "더 있을 수 있다" 고 하지 않고 목록 꼬리의 값까지 본다. 확인: 상한
    판정 줄이 거르기 전 목록의 개수만 보는지, 서버 정렬 키가 거르는 값과 같은지 본다. 언제: 서버 목록을 값으로 걸러 낸 뒤 상한·"더 있음"
    안내를 정하는 diff.
14. **실패를 여럿 모으는 반복에서 첫 실패만 기억.** 반복 안에서 예외를 잡아 모을 때 첫 예외만 남기면, 뒤에 온 요청 제한을 보고도 멈추지
    않고 안내 이유도 첫 실패의 것이 된다. 멈춤(요청 제한이면 남은 요청을 보내지 않음)은 실패마다 정하고, 안내는 무엇으로 정하는지 적는다.
    확인: 실패 순서를 바꿔(5xx 다음 요청 제한) 넣어 남은 요청이 나가는지 본다. 언제: 반복 안에서 예외를 잡아 건너뛰거나 모으는 `+` 줄.
15. **상태 파일에서 읽은 큰 정수.** 상태 파일(`<state_dir>` 아래 JSON)에서 읽은 정수를 실수와 빼거나 `float()`·`isfinite` 에 넘기면, 약
    1.8×10³⁰⁸ 이상인 정수에서 OverflowError 가 나 그 소스의 모든 명령이 `INTERNAL_ERROR` 다. 한 번 비교에만 쓰면 빼지 않고 비교로 쓰고, 뒤에서
    실수로 바꿔 쓰면 읽는 자리에서 버린다. 확인: 그 칸에 `1` 뒤에 0 을 400개 붙인 정수를 넣고 명령을 불러 본다. 언제: 상태 파일을 읽는 코드나
    거기서 읽은 시각·수를 계산하는 `+` 줄.
16. **소스 전용 재시도 술어·에러 매핑이 상태 코드에 붙인 뜻에서 첫 화면 단계 에러를 거르는가.** "500 은 요청 값 때문이라 다시 보내도 같다" 처럼
    소스 고유 뜻을 상태 코드에 붙이면, 첫 화면 문서(홈 HTML)의 상태 코드는 API 응답과 뜻이 달라 `EntryOpenError` 를 물려받은 에러(`EntryStatusError`
    등)를 먼저 걸러 내지 않는 한 사이트 장애를 재시도하지 않거나 입력 오류로 안내한다. 확인: 그 술어에 `EntryStatusError(500)` 과 API
    `HTTPStatusError(500)` 을 넣어 불러 본다. 예: `providers/skyscanner/api/client.py:60` `should_retry_skyscanner` (그때 첫 화면 500 도 재시도하지
    않았다, 2026-11-24 리뷰). 언제: 재시도 술어나 `HTTPStatusError` 의 상태 코드로 가르는 갈래를 더하거나 바꾼 diff.
17. **브라우저 이동 실패가 숨긴 상태 코드.** 첫 화면 문서의 4xx·5xx 판정을 `page.goto` 가 돌려준 응답에만 기대지 않는가. Chromium 은 본문 없는 4xx·5xx 문서에서
    goto 를 `net::ERR_HTTP_RESPONSE_CODE_FAILURE` 로 실패시켜 응답을 돌려주지 않는다. 확인: 가짜 첫 화면이 `Content-Length: 0` 으로 403·429·503 을 주게 하고
    에러 종류·쿨다운과 함께 닫은 뒤 쿠키 파일·기록 폴더가 지워졌는지도 본문이 있는 경우와 비교한다 (`scripts/ci/browser_check.py` 16번이
    이 경우를 본다. 정리는 에러 판정이 맞아도 따로 빠질 수 있다: 그 갈래에서 컨텍스트를 두기 전에 `_close` 를 불러 거부된 쿠키·기록 폴더가
    남았다, 2026-11-24 두 번째 리뷰). 예: `core/browser.py:1960` `_launch` 의 except 갈래(`HTTP_RESPONSE_CODE_NET_ERROR`) (그때 연결 오류로 보고
    재시도한 뒤 `NETWORK_ERROR` 로 냈고 쿨다운·차단 판정이 빠졌다, 2026-11-24 리뷰). 언제: 첫 화면 문서 상태로 판정하는 코드나 `goto`·`_entry_error` 의 예외 처리를 바꾼 diff.

## `contract` 출력 계약

1. **안내를 따르면 되는가 (모든 모드에서).** `--limit` 이 이미 최대값인데 늘리라고 하지 않는가. 좁히라고 권하는 것(날짜·직항·항공사)이 그
   명령·소스에 실제로 있는가. 안내가 말하는 원인이 실제 원인과 맞는가. 확인: `notes`·`hint` 에 든 옵션과 이유를 그 명령의 옵션 검사·서버 동작과
   대조한다. 예: `providers/naver/service/calendar.py:124-131` (그때 `calendar` 가 1년 넘는 달이 비면 서버가 날짜별 최저가를 주는 범위 밖이어서인데도
   "검색한 사람이 적으면" 이라는 틀린 이유를 냈다. 지금은 서버가 준 가장 늦은 날과 견줘 범위 밖이라고 알린다, 2026-11-01).
   언제: `notes`·`hint`·에러 message 를 바꾸거나 한 명령에 옵션을 더한 diff, `core/`·`cli/` 공용 모듈이 모든 명령에 붙이는 hint.
2. **예시 이름과 권하는 명령.** hint 의 예시·명령을 그대로 넣으면 그 명령이 받는가 (공항 코드를 받지 않는 옵션에 코드, 여전히 모호한 예시,
   필수 옵션을 빼라는 안내). 확인: 예시를 그 명령의 인자 검사에 넣어 따라간다. 언제: hint·notes·에러 message 에 `baenggipyo ` 명령이나 예시
   이름이 든 `+` 줄, 여러 명령이 함께 쓰는 hint 를 새 명령이 부르게 한 diff.
3. **한 결과 안 안내끼리.** "전부입니다" 와 "더 있을 수 있다", 같은 안내 여러 번, '편'·'건' 섞임이 함께 나오지 않는가. 같은 목록을 안내마다 다른
   이름으로 부르지도 않는가. 확인: 여러 갈래가 함께 참이 되는 입력을 찾는다. 언제: 한 결과에 안내를 붙이는 갈래가 둘 이상인 함수를 바꾼 diff.
4. **에러 code·hint 가 원인과 맞는가.** 응답 5xx 를 "스펙 변경" 으로, 형식 오류 400 을 "없는 ID" 로, 정상 0건을 에러로 알리지 않는가.
   감시·에이전트가 hint 문구가 아니라 `code`·`reason` 같은 필드로 가르는가. hint 가 권하는 행동이 그 원인에서 소용 있는가. 예:
   `core/ratelimit.py:91-105` `StateDirError` (그때 상태 폴더에 못 쓰면 `INTERNAL_ERROR` 에 "다른 소스를 쓰라" 는 hint 가 나왔다. 두 소스가 같은
   폴더를 써 다른 소스도 같이 실패하므로 소용없었다. 지금은 `BAENGGIPYO_STATE_DIR` 로 쓸 수 있는 경로를 주라고 안내한다, 2026-11-01).
   같은 `code`·`status` 가 다른 원인(API 응답과 첫 화면 문서)에서 나오면 매일 감시 `_is_unknown` 이 hint 와 같은 판정(사이트 장애면 확인 못 함)을
   내릴 수 있게 원인을 가르는 필드(`entry_page`, `reason`)가 있는지도 본다 (`scripts/monitor/api_check.py:135` `_is_unknown`, 그때 첫 화면 500 은
   "사이트 장애" 안내인데 감시는 고장으로 셌다, 2026-11-24 리뷰).
   언제: 에러 클래스·`code`·hint 를 고르는 갈래나 `raise ...Error(` 를 더하거나 바꾼 diff, `scripts/monitor/api_check.py` 의 판정을 바꾼 diff.
5. **사용법 오류 안내가 그 명령 기준인가.** 다른 명령의 hint 를 물려받아 원래 없던 옵션을 "없앴습니다" 라고 하지 않는가. 한 값 옵션을 반복해
   마지막 값만 남는 것, 쉼표로 여럿 준 값을 그 명령이 막는지 본다. 언제: 옵션 검사·사용법 오류(`BadParameter`)를 바꾼 diff, 옵션을 더하거나
   `list` 로 선언을 바꾼 diff.
6. **help·Field description·`docs/<source>.md` 가 동작과 같은가.** 기본값·거르기를 바꾼 diff 면 셋을 함께 grep 한다. 동작 문장은 명령
   입구(CLI 옵션 검사)부터 따라가 확인한다. 서비스 함수만 보면 CLI 가 그 앞에서 막는 조합까지 된다고 적게 된다. 문서가 코드를 보지 않고
   쓰인 것은 아닌지도 본다. 예: `providers/naver/service/flight.py:475-489` (그때 `docs/naver.md` 는 국제선 `flight` 를 검색 15분 뒤 불러도 알린다고
   적었으나 실제로는 서버가 버전 없는 조회에 조용히 새로 검색해 만료 안내가 없었다. 문서와 코드를 함께 고쳤다, 2026-11-01).
   요청 경로(브라우저·첫 화면 단계 등)를 바꿔 걸리는 시간이나 `limits` 에 쌓이는 요청 수가 달라졌으면 help·`docs/<source>.md`·`docs/llm.md` 의 소요
   시간·요청 수 문구도 grep 한다 (`cli/skyscanner.py:146` "보통 10~25초", 그때 "보통 5~15초" 가 남아 실측 18초와 어긋났다, 2026-11-24 리뷰).
   언제: 기본값·거르기·옵션·출력 필드를 바꾼 diff (help·`Field(description=`·`docs/<source>.md` 중 일부만 바뀌었으면 특히), 요청 경로를 바꿔 소요 시간·요청
   수가 달라진 diff, 여러 명령을 한 문장에 묶어 설명한 diff.
7. **코드를 말로 바꾸는 표에서 모르는 코드.** `.get(코드)` 로 모르는 코드를 `None` 으로 버리면 '서버가 주지 않음(`null`)' 으로 읽힌다. 다른
   표처럼 `.get(코드, 코드)` 로 원본을 남기거나, 버린다면 설명에 적었는가. 확인: 새 이름표 dict 를 쓰는 `.get(` 의 두 번째 인자와 Field
   설명의 `null` 뜻을 대 본다. 언제: 서버 코드 → 한국어 이름표 dict 를 새로 두거나 값을 더하는 diff.
8. **문서에 적은 값의 뜻을 응답 키·상수로.** 문서·Field description 이 적은 값의 뜻(빈 목록이 무엇을 뜻하는지, 시각이 어느 시각인지)이 그
   필드를 채우는 응답 키와 서버가 쓰는 모든 값과 맞는가. 확인: 필드를 채우는 줄의 응답 키를 보고, 표에 없는 값까지 원본 응답에서 grep 한다.
   언제: 새 출력 필드의 뜻이나 빈 값의 뜻을 문서·Field description 에 적은 diff, 기존 필드에 값이 나오는 곳을 더한 diff (전에 맞던 "비면 …"
   문장이 새 조합에서 틀린다).
9. **한 시점의 웹 동작으로 단정하지 않는가.** 문서·안내가 웹 동작을 근거로 에이전트 행동을 정할 때, 그 말이 본 날의 화면에서만 맞지 않는가
   (사이트가 코드를 바꾸면 그 단정만 낡는다). 확인: 단정이 기대는 웹 동작을 직접 봤는지, 소스 가이드가 "확인하지 못했다" 고 적은 항목까지 한데
   묶었는지 본다. 언제: `docs/llm.md`·`docs/<source>.md` 에 웹 화면 동작을 근거로 쓰는 쪽의 행동을 정한 문장.
10. **날짜·시각을 못 읽으면 원래 글자를 돌려주지 않는가.** 변환 함수가 못 읽을 때 원래 글자를 돌려주면 `YYYY-MM-DD`·`YYYY-MM-DDTHH:MM` 이라고 적은
    필드에 다른 모양이 나간다. 확인: 날짜·시각 필드를 채우는 줄이 어느 함수를 부르는지와 Field 설명을 대 본다. 언제: 날짜·시각 필드를 더한 diff.
11. **유형을 모르면 줄을 통째로 버리는 변환.** `… | None` 을 돌려주는 변환 함수가 모르는 운임·좌석 유형에 `None` 을 주고 호출부가 그 줄을 빼면, 버린
    수를 세어 `notes` 로 알리는가. 알리지 않으면 항공권이 말없이 사라진다. 확인: 변환 결과가 `None` 일 때 건너뛰기로 끝나는 자리마다 센 수가
    `notes` 에 가는지 본다 (`--limit` 으로 어차피 잘릴 자리는 세지 않아도 된다). 언제: 변환 함수가 `None` 을 돌려주는 갈래를 더하거나 그 결과로
    줄을 빼는 diff.
12. **다른 명령을 권하는 안내가 사용자가 붙인 앞 낱말을 버리지 않는가.** 같은 이름을 가리려고 사용자가 앞에 붙인 낱말을 빼고 찾은 이름만 권하면,
    권한 명령을 그대로 불렀을 때 `AIRPORT_AMBIGUOUS` 가 난다. 확인: 안내에 든 명령을 그대로 불러 같은 곳을 찾는지 본다. 언제: 안내·`hint` 가 다른
    명령과 그 검색어를 글로 알리는 `+` 줄.
13. **에러 `details` 의 None 을 빼지 않는가.** `details` 의 None 은 모름이라 출력에 `null` 로 남아야 한다 ([에러](output-contract.md#에러)). 확인:
    None 이 들어갈 수 있는 details 를 던지는 에러를 `handle_errors` 안에서 던져 stderr JSON 에 그 키가 `null` 로 있는지 본다. 언제: 에러 details 에
    None 일 수 있는 값을 넣거나 `emit_error`·`handle_errors` 를 고칠 때.
14. **요약 출력에서 뺀 키가 사실을 지우지 않는가.** `--brief` 가 `brief_omitted_fields` 로 키를 빼도, 그 키가 알려 주던 사실은 다른 칸에 남아야 한다
    ([요약](output-contract.md#요약---brief)). 확인: 요약에서 빼는 키마다 그 키가 없으면 잃는 사실이 다른 칸에 남는지, 같은 항공권을 `--brief`·`--full`
    로 불러 견준다. 예: `core/flight.py:514` `Segment.brief_omitted_fields` (그때 구간 공항을 요약에서 빼, 공항을 옮겨 갈아탈 때 도착 공항과 다음 편의
    출발 공항이 다르다는 사실이 사라졌다. 지금은 `Journey.restore_brief` 가 바뀌는 두 끝만 되돌린다, 2026-11-01).
    언제: `brief_omitted_fields` 에 키를 더하거나 요약 출력의 모양을 바꾼 diff.
15. **사이트가 준 주소를 출력에 그대로 싣지 않는다.** 에러 message·hint·details·`--verbose` 로그에 사이트가 준 주소(`page.url`, 리다이렉트 주소, `response.url`)를 넣으면
    로그인·보안 확인 화면의 쿼리·경로에 실린 토큰이 나간다 ([내보내지 않는 정보](output-contract.md#내보내지-않는-정보)). 출처만 싣는다. 확인: 가짜 첫 화면이 다른 출처의
    `?token=secret` 주소로 302 하게 하고 에러 JSON 을 본다. 예: `core/browser.py:1509` `finish_entry` 다른 출처 갈래 (그때 `?token=…` 이 message 에 그대로 나갔다, 2026-11-24 리뷰).
    언제: `page.url`·`response.url`·리다이렉트 주소를 문자열에 넣는 `+` 줄.
16. **에러에 싣는 응답 본문의 비밀 값을 글 모양마다 가리는가.** 4xx·5xx 본문을 에러 message 에 실을 때(`_body_preview`) JSON 으로 읽히는 본문은
    키로 가리지만(`_redact_json`), 그 밖의 본문은 `SENSITIVE_TEXT_PATTERN` 하나가 가린다. 키 뒤 따옴표만 건너뛰면 HTML 스크립트의 JS 문자열 안
    JSON(`"{\"token\":\"…\"}"`)은 역슬래시에서 멈춰 값을 못 가리고, `Authorization: Bearer …` 는 `Bearer` 만 가려 그 뒤 값이 나가며, 값을 공백에서
    끊으면 `Cookie: a=…; b=…` 의 두 번째 쿠키부터 나간다 ([내보내지 않는 정보](output-contract.md#내보내지-않는-정보)). 확인: `{"accessToken":"X"}` 를 담은
    HTML, `"{\"token\":\"X\"}"` 를 담은 HTML, `Authorization: Bearer X`, `Cookie: a=1; b=X`, `token=X` 를 본문으로 준 500 응답에 `raise_for_status` 를 불러
    message 에 `X` 가 남지 않는지 본다. 예: `core/http.py:95` `SENSITIVE_TEXT_PATTERN`·`COOKIE_TEXT_PATTERN` (그때 따옴표 친 키만 가리고 뒤의 세 꼴은 값이
    그대로 나갔다. 지금은 `\"`·인증 방식 낱말을 건너뛰고 쿠키 줄은 줄 끝까지 가린다, 2026-11-24).
    언제: `SENSITIVE_*` 패턴·`_redact_*`·`_body_preview` 를 바꾼 diff, 서버가 준 글자를 에러 message·로그에 새로 싣는 `+` 줄.

## `web` 웹 대응

1. **웹 식을 옮길 때 JS 의미까지.** `??` 와 `||`(0·빈 글자), `Math.round` 와 Python `round`(은행가 반올림), `toFixed` 와 Python `round`·
   `f'{x:.nf}'`, 정수 버림, 안정 정렬, "첫 항목 기준" 같은 기준점. 곳마다 따로 흉내 내지 말고 한 함수로 옮긴다. 확인: 주석의 웹 식과 한 줄씩
   대조하고 0·x.5·동점·첫 항목 없음을 넣어 본다. 그 식이 **그 칸을 그리는 화면**의 식인지도 본다. 같은 값도 화면마다 다르게 그린다.
   언제: 주석에 웹 식(JS)이 붙은 계산, 또는 `round(`·`//`·`sorted(`·`max(`·`min(` 이 든 `+` 줄.
2. **웹이 보내는 변수 모양 그대로인가.** 조건이 없으면 웹처럼 null 을 보내는가(빈 객체·빈 목록이 아니라), 웹 화면이 받는 단위를 넘는 조합을
   만들지 않는가. 첫 요청의 헤더·변수를 검색 종류로 가르면, 같은 세션을 이어 받는 요청(폴링·다음 쪽)도 같은 갈래를 쓰는가 (사례: `providers/skyscanner/api/client.py:241` `_search_headers`, 어디든지 검색의 폴링이 항공권 검색 헤더를 붙였다, 2026-11-24 리뷰).
   언제: `api/request/` 의 변수·쿼리 모양이나 그 기본값을 바꾼 diff, 또는 요청 헤더를 고르는 갈래를 바꾼 diff.
3. **사이트에 없는 결과.** 사용자가 고르지 않은 기준으로 받은 결과를 거르거나 웹에서 고를 수 없는 기준으로 다시 줄 세우거나 다른 소스로 대신 찾지 않는가, 후보 중 하나를 임의로 고르지 않는가
   (위 `correctness` 4), `notes` 가 실제로 없는 사유("조건 불일치")를 말하지 않는가. 언제: 받은 목록을 거르기·합치기·다시 정렬하기·고르기 하는
   `+` 줄, 뺀 항공권을 알리는 `notes` 문구.
4. **웹과 다른 개선을 적었는가.** 웹에 없는 동작이 그 소스 개발 가이드의 "웹과 다른 점" 절(없으면 만든다)에 있는가. 언제: 웹에 없는
   옵션·기본값·묶어 받기를 더한 diff.

## `requests` 요청 수·차단 위험

1. **이미 아는 것을 다시 묻지 않는가.** 앞 결과·방금 받은 응답으로 아는 값을 다시 묻거나, 답이 같을 두 번째 요청을 보내지 않는가. 확인: 루프·후속
   검사 안의 공항 찾기·검색 호출이 결과를 바꿀 입력이 실제로 있는지 따진다. 언제: 루프·후속 검사 안에 공항 찾기·검색·client 호출이 든 `+` 줄.
2. **결과가 정해진 뒤의 요청.** 더 없음을 알면서 빈 응답을 한 번 더 받거나, 끝났다는 표시가 없는 응답을 믿고 폴링 상한까지 묻지 않는가.
   언제: 폴링·쪽 넘기기 루프의 멈춤 조건을 바꾼 diff (`correctness-1` 과 같은 자리).
3. **덤 조회의 순서와 실패.** 판매처 수 세기·이름 찾기 같은 덤 조회를 본 조회 뒤에 하는가, 덤이 실패(요청 제한 포함)해도 받은 결과를 버리지
   않는가. 언제: 덤 조회를 더하거나 순서를 바꾼 diff.
4. **요청 전에 막을 수 있는 입력.** 결과와 상관없이 막힐 입력을 요청 뒤에 막지 않는가 (이름 모양으로 짐작해야만 막을 수 있으면 아래 "지적하지
   말 것" 3). 언제: 입력 검사·에러를 요청 뒤에 두는 `+` 줄.
5. **요청 제한 훅을 거치지 않는 요청과 서버 신호 (`core/`).** 폴링으로 다시 묻는 요청·redirect 도 훅을 거치는가, `Retry-After` 보다 짧게 쉬지
   않는가, 429 뒤에 같은 요청을 곧바로 쏟지 않는가. 브라우저 첫 화면이 스스로 보내는 요청은 transport 가 `RateLimiter.record` 로 센다 (소스마다 끌 수 있고 스카이스캐너는 끈다). 언제: `core/http.py`·`core/ratelimit.py`·`core/browser.py`·소스 `api/client.py` 를 바꾼 diff.

## `design` 구조·중복·단순화

1. **같은 규칙 두 벌.** 같은 판정식·문구·흐름·필터가 다른 함수·파일에 또 있는가, 이미 있는 helper 를 다시 만들었는가. 공통 함수가 생긴 뒤에도 한
   소스가 손으로 쓴 문장을 남기면 그 소스만 갈래가 빠진다. 확인: 새 함수·식·문구의 핵심 낱말로 grep 한다. 언제: 새 함수·상수·문구·필터·갈래를
   더한 diff, `core/` 에 두 소스용 함수를 더하거나 바꾼 diff (그 일을 하는 소스별 문장을 grep 한다).
2. **호출부마다 달라야 할 인자에 기본값.** 호출부마다 값이 달라야 맞는 인자에 기본값을 두면 빠뜨려도 조용히 틀린다. 설정을 dict 로 `**` 풀어
   넘기지 않는다. 언제: 기본값이 있는 인자를 더하거나, 설정 dict 를 `**` 로 넘기는 `+` 줄.
3. **닿지 않는 갈래·쓰지 않는 인자.** 부르는 곳이 사라진 갈래·예외 클래스, 받기만 하고 쓰지 않는 인자, 늘 같은 값(`[]`·`None`)만 돌려주게 된 반환값과
   그 값을 받아 잇는 호출부가 남지 않았는가. 확인: 갈래를 지운 함수의 `return` 을 모두 보고 호출부를 grep 한다. 언제: 코드를 지우거나, 부르는 곳을
   옮기거나, 인자를 더한 diff, 함수의 갈래를 지워 돌려주는 값이 줄어든 diff, 선택이던 인자를 모든 호출부에서 늘 넘기게 바꾼 diff.
4. **따로 도는 CI 단계가 지키는 파일.** 그 단계도 통과하는가. 확인: `docs/llm.md` 나 `guide` 출력 코드를 바꿨으면 `.github/workflows/ci.yml` 의
   `docs/llm.md` 200줄 검사와 `guide` 세 출력(`guide`·`guide naver`·`guide skyscanner`)을 이어 문서와 비교하는 단계를 대 본다. 언제:
   `docs/llm.md`·`cli/app.py` 의 `guide` 를 바꾼 diff.

## `convention` 규약 위반

1. **조사.** 이름 뒤 조사는 `particle`·`quoted` 로 고르고, '으로/로' 처럼 받지 않는 쌍은 문장을 바꾼다 ([코드 형식 §1](code-style.md#1-언어)).
   언제: f-string 의 `{이름}`·`{숫자}` 바로 뒤나 한 칸 띄고 조사('이'·'가'·'을'·'를'·'은'·'는'·'으로'·'로')가 붙은 `+` 줄 (`HTTP {entry_status} 로` 가 '사백삼으로' 와 어긋났다, 2026-11-24 리뷰).
2. **바뀐 동작 근처의 주석·docstring.** 동작을 바꾼 diff 면 그 함수 docstring·주변 주석(요청 수, 예시, `리뷰 오탐` 주석)이 새 동작과 맞는가.
   언제: 동작을 바꾼 diff 에서 그 함수의 docstring·주석이 함께 바뀌지 않았을 때.
3. **금액·시각 규칙.** 금액은 원 정수이고 필드 이름이 `_krw` 로 끝나는가. 총액과 1인 요금을 이름으로 구분하고, 소스가 한쪽만 주면 다른 쪽을
   나눗셈·곱셈으로 만들지 않았는가. 다른 통화로 오면 환율을 추측하지 않는가. 시각은 각 공항의 현지 시각이고 시간대를 환산하지 않는가
   ([금액·시각·코드](output-contract.md#금액시각코드)). 언제: `*_krw` 를 만들거나, 가격을 계산하는 `+` 줄, 시각·소요 시간을 바꾸는 `+` 줄.
4. **CHANGELOG 절.** 문구·안내만 바뀐 줄은 `변경`, 받던 입력을 더는 받지 않거나 출력 꼴이 바뀐 줄은 `⚠️ 호환 깨짐` 이다
   ([CHANGELOG 쓰는 법](release.md#changelog-쓰는-법)). 다만 예전 안내·도움말이 실제 동작과 달랐던 것을 바로잡은 줄은 `수정`(문서 오류)이다.
   에러 `code` 가 바뀐 줄과 라이브러리로 쓰는 함수의 예외·반환 모양이 바뀐 줄도 `⚠️ 호환 깨짐` 이다. 같은 diff 의 같은 종류 변경이 한 절에 모였는지
   본다. 반대로 사용자(에이전트 포함)에게 보이는 출력·에러 `code`·옵션·`notes`·도움말이 바뀌었는데 `Unreleased` 에 줄이 없는지도 본다. 언제:
   `CHANGELOG.md` 에 줄을 더한 diff, 또는 `src/` 에서 출력·에러·옵션을 바꾼 diff.
5. **운용 규칙은 원문 한 곳.** 같은 규칙(작업자가 다르게 해도 되는 범위, 모델 기준, 검증 범위)을 `docs/development/agents.md`·`CLAUDE.md`·에이전트
   정의·워크플로·skill 에 따로 옮겨 적지 않고 원문 한 곳을 가리키는가. 바꾼 규칙과 같은 주제의 다른 문장도 함께 바뀌었는가. 언제: `.claude/`·
   `CLAUDE.md`·`AGENTS.md`·`docs/development/agents.md` 를 고친 diff.
6. **같은 소스의 기능 모듈끼리 import 하지 않기.** `service/` 의 새 import 가 [provider-conventions.md](provider-conventions.md#service-모듈을-나누는-기준)
   기준 3 의 import 방향(`common` → `airport` → 기능 모듈 → 분기 모듈)을 따르는가. 확인: diff 의 `+from baenggipyo.providers.<source>.service.<기능>`
   줄. 언제: `service/` 에 새 import 를 더한 diff.
7. **감시 단계가 비면 고장으로 잡히는 노선인가.** 새 `Step` 은 결과 0건을 고장으로 본다. 그래서 인기 노선·넉넉한 날짜로 불러야 거짓 고장이 안 난다.
   국제선·국내선이 다르게 동작하면 둘 다 넣었는가 ([매일 API 감시](README.md#매일-api-감시)). 언제: `GROUPS` 에 `Step` 을 더하거나 인자를 바꾼 diff.

## 지적하지 말 것

일부러 다르게 둔 이유가 코드·주석·소스 가이드에 있으면 지적하지 않는다. 다만 `# 리뷰 오탐` 주석이라도 근거가 "실측에 없었다"·
"문서에 그렇게 적었다" 뿐이면 이유가 아니다 ([코드 리뷰](agents.md#코드-리뷰) 2단계·3단계. 문서는 코드를 보고 쓴 것이라 제자리를 돈다).
주석이 설명하는 동작이 실제 코드 동작과 다르면 그 주석도 이유가 아니다. 그런 자리는 서버가 보낼 수 있는 값으로 다시 따져 지적해도 된다.

1. **"비슷한 두 함수·검사를 합쳐라".** 입력 형식, 실패 시 계약, 요청 수를 세는 법, 층의 책임, 검사 시점, 호출마다 다른 에러 문구가 달라서 따로 둔
   것은 합치면 출력이 바뀌거나 갈래 인자가 붙은 함수가 된다. 그 차이가 주석에 있으면 지적하지 않는다 (없으면 `design` 1 대로 지적한다).
2. **닿지 않는 경로의 틀린 값.** 모든 호출부가 돌려받은 값을 바로 거절하거나, 값이 Literal 고정이라 받침이 늘 있거나, 앞 상한에 먼저 닿아 그 갈래에
   가지 않으면 오탐이다. 지적하기 전에 그 갈래에 닿는 입력을 하나 댈 수 있어야 한다.
3. **"요청 전에 막아라" (이름을 찾아봐야 종류를 아는 경우).** 도시인지 공항인지 이름 모양으로 짐작해 막으면 잘못 막는다.
4. **"0 과 null, null 과 키 삭제를 통일하라".** 값 없음 규칙(모름 `null`, 해당 없음 키 삭제, 없음 `[]`)은 칸의 뜻으로 가른 것이다. 웹이 0 을 그리는
   법('0원' 이냐 '정보 없음' 이냐)이 칸마다 다르고, 웹이 그릴 수 있는 칸인데 값만 없으면 해당 없음이 아니라 모름(`null`)이다.
5. **"응답 모델 칸의 자료형이 바뀌면 그 응답을 같이 읽는 다른 명령까지 `PARSE_ERROR` 가 된다".** 글자 칸에 숫자가 오는 것처럼 응답 형식이 바뀌는 일은
   [매일 API 감시](README.md#매일-api-감시)가 잡는 고장이라 칸마다 받는 형식을 미리 넓혀 두지 않는다 ([코드 리뷰](agents.md#코드-리뷰) 2단계).
   서버가 소수·0 처럼 지금 값의 연장을 줄 수 있는 칸(`correctness` 6)과는 다르다.
